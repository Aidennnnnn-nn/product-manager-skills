# 个人产品工作标准

## 适用范围

当任务涉及 PRD、产品原型、UI、交互、按钮或操作命名、Figma/HTML 原型交付、需求与原型回读时使用本标准。

本 Skill 是跨项目的个人工作标准，不承载任何公司的品牌、平台名称、业务对象、具体菜单、Figma 文件、项目目录或项目专用尺寸。进入具体项目后，必须同时读取项目根目录 `AGENTS.md` 和项目指定的全局规则。

## 对外可移植性与版本

- 当前版本为 `V1.0`，按可公开阅读、可跨项目安装和可独立理解的方式维护。
- Skill 中不得写入公司或项目专属路径、内部账号、私有链接、访问凭据、敏感数据或未脱敏业务样例。
- 项目实践只抽象为通用判断、流程和质量门禁；品牌、菜单、业务对象、权限边界、项目目录和专用文件名继续由项目规则维护。
- 只有用户明确指定时，才允许升级版本、创建版本 Tag 或发布新的 GitHub Release；普通内容调整不自动改变发布版本。

## 规则分层

按以下优先级执行：

1. 用户当前明确要求。
2. 当前项目已确认规范。
3. 本个人产品工作标准。
4. 历史材料、参考稿和未确认方案。

项目规则只能约束对应项目，不能自动升级为个人标准。单一页面特例、截图偶然值和未确认方案不得直接写入本 Skill。

### 全局规范沉淀门禁

当用户提出“记录为全局规范”“沉淀为全局要求”“后续统一遵循”或同类要求时，不能据此直接修改本 Skill 或其他全局 Skill。必须先：

1. 判断该规则应属于项目级规范、全局提示词，还是某个个人专项 Skill。
2. 向用户说明建议写入的具体文件或 Skill、规则内容、适用范围，以及对现有规则的影响。
3. 明确询问用户是否将该规则落实到对应全局 Skill。

只有用户再次明确确认后，才能执行全局 Skill 写入。“记录为全局规范”只表示希望长期复用，不等同于已经授权修改 Skill；未获确认时，只保留为当前会话决定或项目规则。

## 新会话启动

开始实际写入或生成前：

1. 确认任务目标、范围、对象、角色、用途和关键口径。
2. 读取当前工作目录及其适用的 `AGENTS.md`。
3. 找出当前项目的规则入口、源文件和已确认版本。
4. 区分个人标准、项目规则、当前任务要求、历史事实和待确认内容。
5. 判断上游 PRD、HTML 原型、Figma 或外部来源是否已经确认。
6. 对新建、移动、删除文件或文件夹，先说明目标路径、影响范围和非目标内容；用户确认后执行。

## 通用产品工作要求

- 信息不足以确定方向时，先提出必要澄清，不基于关键假设生成正式产物。
- 未确认内容使用“待确认”，并说明需要确认的对象和后续动作。
- 不扩大用户明确限定的范围；发现父需求与子项范围不同步时，按用户指定层级处理。
- 当前项目文件和用户最新要求优先于本地知识库和历史材料。
- 修改长文档前先读取当前版本，使用最小范围修改，并回读检查旧文案、旧链接和结构残留。
- 交付说明区分静态检查、浏览器交互检查、视觉检查和人工确认，不把一种证据冒充另一种证据。
- 面向用户阅读、汇报、归档和交付的素材优先使用清晰中文命名；必要时保留 API、JSON、CSV、V1 等技术标识。

## PRD 通用要求

PRD 的具体格式和编号由适用的 PRD Skill 与项目规范决定。本 Skill 只规定通用判断：

- 明确背景、问题、目标、非目标、用户、场景和本期范围。
- 让功能需求、业务规则、状态、异常、权限、数据范围和验收标准可以互相追踪。
- 聚焦产品和业务落地，不主动扩写数据库、接口实现和技术方案。
- 需求编号、修订记录和待确认项必须稳定、可追溯。
- 未确认的业务语义不能直接冻结为页面、字段或交互规则。
- PRD 是 HTML 原型和 Figma 原型的上游依据；PRD 未确认时，不自动进入原型阶段。

使用标准 PRD 时继续调用 `pm-execution-create-prd`；不要在本 Skill 中复制或覆盖该 Skill 的模板细节。

## 专项 Skill 分工

个人产品工作当前只维护两个专项 Skill，避免把相近能力拆成过多独立入口：

1. `pm-execution-create-prd`：个人 PRD Skill。负责 PRD 结构、需求追踪、业务规则、状态、权限、验收，以及按钮名称、操作命名、字段文案和反馈文案偏好。
2. `pm-prototype-workflow`：个人原型绘制 Skill。负责 HTML/Figma 原型、UI 基线、交互状态、页面布局、组件表现、视觉检查和原型交付。

使用边界：

- PRD 中先定义动作语义、业务结果、权限和文案；原型 Skill 负责把已确认语义表现为页面、状态和可操作交互。
- UI 与交互规则统一放在原型绘制 Skill，不在总控 Skill 中重复维护。
- 按钮名称、字段文案和操作文案偏好统一放在 PRD Skill；项目词表仍由项目规则覆盖。
- 已验证项目中的 UI 与交互实践可作为原型绘制 Skill 的方法来源；进入具体项目后仍必须读取项目文件，以项目最新确认内容为准。
- UI 与原型绘制统一以 `pm-prototype-workflow` 为个人标准，不自动叠加其他个人、团队或第三方 UI Skill。只有用户在当前任务中明确指定时，才可加载为补充参考。
- 完整规格驱动开发、专项调研、指标和测试场景等现有 Skill 暂不纳入本次个人 Skill 主线，除非用户另行要求。

## 个人 Skill 命名规范

后续新增个人产品 Skill 统一使用以下命名格式：

```text
pm-<能力>-<任务或场景>
```

命名要求：

1. 目录名全部使用小写英文、数字和短横线，不使用中文、空格、下划线、斜杠或版本号。
2. `pm-` 表示产品经理工作域；能力使用稳定短词，例如 `prd`、`prototype`、`research`、`review`、`metrics`。
3. 任务或场景只保留能帮助 Skill 检索和区分的必要信息，不添加无意义的 `skill`、`standard`、`tool`、`v1`、日期或项目名称。
4. 中文名称、适用范围、触发条件和详细说明写在 `SKILL.md` 的 `description` 和正文中，不塞入目录名。
5. 同一能力域优先使用统一前缀，例如 `pm-prd-*`、`pm-prototype-*`；只有能力边界确实不同才创建新的前缀。

当前 `pm-prototype-workflow` 已按本规则完成命名；`product-work-standards` 和 `pm-execution-create-prd` 属于已存在的兼容名称，不因本规则自动移动或重命名。后续如需迁移其他现有 Skill，必须先列出目录、引用和自动发现影响，再单独确认。

## 不确定规则的处理

当发现项目规则可能适合泛化时，按“先验证、再抽象、后确认”的方式处理。先记录：

- 当前规则来源和适用项目。
- 已验证的模块或页面。
- 与项目特定事实的耦合点。
- 可能的个人化表达。
- 需要用户确认是否拓展为个人标准的问题。

具体新规则仍需经过多个场景验证、脱离项目特定事实并获得用户确认后，才更新两个个人专项 Skill；任何项目的品牌、菜单、业务对象、权限边界、项目目录和专用文件命名继续留在项目级。
