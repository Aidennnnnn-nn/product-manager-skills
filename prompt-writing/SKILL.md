# 提示词撰写

把业务规则转化为供 AI 理解或调用的提示词。支持新写、润色、批量生成和质量检查，不负责替代业务 Schema、权限系统、运行时校验或实际工具执行。

## 工作原则

- 以用户最新输入和当前项目文件为准；未提供的业务规则不猜测为既有事实。
- 先识别提示词的使用对象、目标行为、可用输入、预期输出和禁止行为。只有关键口径缺失且不同选择会改变结果时才询问用户。
- 区分自然语言提示词与结构化配置。已有独立字段承载的标识符、类型、范围、权限或运行环境信息，不机械重复到提示词中。
- 只保留会改变 AI 识别、转换、决策或反馈方式的内容。避免背景介绍、同义反复、口号和无法验证的要求。
- 最终文本默认使用直接、连贯的自然语言。内部检查框架不自动成为提示词标题。
- 批量生成前先用少量代表性样例确认格式；未获确认时不扩展到全量数据。
- 修改用户提供的真实文件时，严格限制在用户确认的范围内，并验证内容和格式。

## 控制功能标识符命名

当任务包含新定义、补充或修正 IOT 控制功能标识符时，遵循以下规则：

- 标识符使用大驼峰命名法（PascalCase），不使用下划线分隔。
- 标识符优先使用能够直接对应业务含义的英文完整单词，确保控制名称可以还原为明确的英文全称；只有行业通用、语义明确、已确认并登记在固定词汇清单中的缩写才允许使用。
- 不允许使用任意截断、拼写残片、未确认缩写或无法还原英文全称的简写。新增缩写必须同时登记中文含义、英文全称、适用范围和标识符写法，经需求提出人确认后才能使用。
- 该规则用于后续新增或重新命名的控制标识符；已确认并投入使用的历史标识符不因该规则自动改名。
- “电池1”或 `Battery1` 统一使用 `Bat1`；“电池2”或 `Battery2` 统一使用 `Bat2`。
- 来源名称中出现 `BMS2` 时，控制功能标识符统一使用 `Bat2`，不保留 `BMS2`。
- 遇到任何电池相关功能时，必须优先依据“电池控制对象判定规则”判断属于第一路电池、第二路电池还是整个电池系统；不得仅根据页面层级、菜单名称或功能名称自行推断。第一路电池使用 `Bat1`，第二路电池使用 `Bat2`，整个电池系统使用 `Bat`；寄存器证据不足或存在冲突时，再向需求提出人确认。
- 电池控制对象未确认前，不得生成最终标识符或写入全量控制标识符库；已确认并投入使用的历史标识符不因该规则回溯修改。
- 功能名称中的“开关”统一使用完整单词 `Enable` 表达，不使用 `En` 等缩写。

### 控制标识符命名流程

0. **判断并确认电池控制对象**
   - 如果功能涉及电池、BMS、电池SOC、电池充放电、电池加热或其他电池相关对象，先按功能描述、分类、前置条件和使用场景判断不同电池路记录是否属于同一功能语义，不得仅因功能名称相同就直接归组。
   - 对同一功能语义，比较第一路和第二路对应的寄存器：寄存器一致，判定为电池系统级，使用 `Bat`；寄存器不一致，判定为电池路级，分别使用 `Bat1` 或 `Bat2`。
   - 同一寄存器被不同功能名称或不同前置条件复用时，不能仅凭寄存器一致就判定为系统级，必须结合使用场景继续确认是否为同一控制项。
   - 缺少寄存器、只有单一路记录、寄存器证据冲突，或功能语义无法归组时，必须向需求提出人确认控制对象；确认前标记为“待确认”，不得生成最终标识符或写入全量控制标识符库。
   - 控制对象确定后，第一路电池使用 `Bat1`，第二路电池使用 `Bat2`，整个电池系统使用 `Bat`。已确认并在库中使用的历史标识符不因新增判定规则自动改名。
1. **匹配全量控制标识符库**
   - 根据功能名称、功能标识符和功能描述，匹配全量控制标识符库。
   - 存在功能名称和使用场景完全一致的唯一记录时，直接推荐并复用已有控制标识符，不重新命名、不重复登记。
   - 存在多个候选项或语义冲突时，不自行选择，标记为待确认。
   - 没有完全一致的匹配项时，必须进入相似概念检测，不得直接重新命名。
   - 当前备注字段统一留空，不通过备注补充命名规则或临时说明。
2. **检测相似概念并确认使用场景**
   - 检索名称不同但业务语义可能相同的已有功能，重点识别同义表达、简称、历史名称、菜单名称和操作文案差异。
   - 用户提供的控制名称重复或高度相似时，先判断它们是同一功能的不同名称，还是不同上级分类、工作模式、时间组或运行场景下的子控制项；不得仅根据名称判重或直接复用同一标识符。
   - 现有信息不足以区分时，必须让需求提出人补充上级分类、使用场景和差异说明；确认前标记为“待确认”，不得生成最终标识符。
   - 确认为不同上级分类下的独立子控制项时，标识符必须加入能够区分业务语义的最小必要上级分类词汇；上级分类只在影响控制语义或用于区分同名子项时加入，不机械拼接全部菜单层级。
   - 上级分类不同，但控制对象、控制目的、执行效果和使用场景完全一致时，仍优先复用已有标识符，不因菜单位置不同重复命名。
   - 用于区分子控制项的上级分类词汇同样必须来自原子词汇库；不存在对应词汇时，按原子词汇缺失流程向需求提出人确认后再补充。
   - 例如“电池即充开关”和“电池快速充电使能”名称不同，但可能是同一个控制项。
   - 例如不同工作模式下均存在“TOU时间组开关”时，必须先确认各自所属模式，再判断是否需要将模式语义纳入标识符，不能直接统一命名为同一个控制标识符。
   - 发现相似候选时，不得直接复用已有标识符，也不得直接创建新标识符；必须主动向需求提出人询问当前功能的控制对象、使用场景、控制目的、执行效果，以及与相似功能的区别。
   - 控制对象、控制目的、执行效果和使用场景均一致时，复用已有标识符；仅名称不同时，将新名称作为同义表达补充到已有功能描述中，不新增功能记录。
   - 使用场景、控制目的或执行效果不同时，确认其为独立功能后再进入重新命名流程。
   - 信息不足以判断时保持待确认，不生成最终标识符，不写入全量控制标识符库。
3. **基于原子词汇库重新命名**
   - 将功能名称拆分为多个原子概念，并为每个原子概念匹配原子词汇库中的英文词汇。
   - 控制标识符统一使用大驼峰命名法，不使用下划线。
   - 不允许使用原子词汇库之外的英文词汇、临时缩写或自行创造的表达。
4. **处理原子词汇缺失**
   - 原子词汇库中不存在对应词汇时，暂停生成最终 key。
   - 先提出候选英文词、候选简称、中文含义和适用范围，向需求提出人确认。
   - 需求提出人确认后，才可将新词加入原子词汇库，并继续生成控制标识符。
   - 未确认前，不得使用该词或绕过原子词汇库直接命名。
5. **命名结果校验**
   - 检查所有组成词是否均存在于原子词汇库。
   - 检查是否符合大驼峰命名法，并检查与全量控制标识符库的 key 冲突。
   - 检查同一中文概念是否被映射为多个英文词。
   - 输出控制标识符、命名来源和原子词组成；备注字段保持为空。

原子词汇库作为控制 key 命名的唯一词汇来源；当前固定词汇清单视为原子词汇库中已确认的词汇集合。

### 全量控制标识符库

- 后续所有控制标识符需求都必须先按本 Skill 的命名流程执行，不得绕过全量控制标识符库直接产出最终 key。
- 唯一承载文件为 [全量控制标识符库](references/全量控制标识符库.md)。每个已确认的控制标识符都必须登记到该文件后，才视为本次命名完成。
- 库中至少登记：功能名称、功能标识符、功能描述。
- 功能描述重点说明功能的使用场景、控制对象和控制目的，不只重复功能名称。
- 后续定义标识符时，必须结合功能描述和使用场景判断是否可以复用已有标识符。
- 只有功能语义、控制对象、控制目的和使用场景均一致时，才允许复用同一个标识符；名称相似但使用场景或控制目的不同，不得仅凭名称复用。
- 同一功能存在不同名称时，只保留一条标识符记录，并在功能描述中补充其他名称作为同义表达，不为同义名称创建新标识符。
- 新增或确认标识符时，同步更新该附属库文件；未确认的候选 key 不得写入库中。

## 属性物模型标识符命名

当任务包含新定义、补充或修正 IOT 属性物模型标识符时，必须调用本 Skill，并参考控制物模型标识符的命名流程执行；属性标识符不直接套用控制标识符的动作语义或 PascalCase 格式。

- 先确认属性的业务对象、数据含义、统计口径、来源字段、数据类型、单位、读写方式和适用设备范围；关键口径缺失或存在多个合理解释时，标记为“待确认”，不得直接定稿。
- 先检索当前项目的属性物模型清单、已确认字段和历史兼容字段，判断是否存在语义、对象、统计口径和使用范围均一致的既有标识符；一致时优先复用，不因中文名称差异重新命名。
- 检测同义字段和近似字段，重点区分实时值、累计值、时间统计值、会话值、设备级值、模式级值和派生值；仅名称相似不能视为同一属性。
- 属性标识符优先使用可还原业务含义的英文完整单词和已确认行业术语，不使用未登记的截断词、临时缩写或拼写残片；新缩写必须先确认中文含义、英文全称、适用范围和标识符写法。
- 属性标识符的大小写和结构以当前项目属性物模型既有规范为准。项目采用 lowerCamelCase 时继续采用 lowerCamelCase，例如 `touPurchaseTotal`；不得因为参考控制物模型而强制改为 PascalCase。
- 属性名应表达稳定的数据字段语义：模式、对象或范围词放在前部，指标或数据含义居中，`Total`、`Stats`、`Status` 等统计或状态限定词放在能够消除歧义的位置；不得仅为追求简短删除必要语义。
- 命名结果必须校验标识符唯一性、英文含义可逆性、大小写格式、类型和单位匹配关系，以及与现有属性标识符的冲突；历史已确认字段不因新规则自动改名。
- 输出属性标识符时，同时说明中文名称、英文名称、数据类型、单位、读写方式、业务描述、命名组成和与相近字段的区分；未确认项明确标注“待确认”。
- 属性物模型标识符不写入全量控制标识符库；如项目存在独立的属性标识符库，应在需求确认后同步登记到对应属性库。

### 寄存器原始协议判定与写回流程

当需求提出人提供寄存器原始协议，并已明确授权根据协议证据判断后写回属性大表时，按以下流程执行：

1. **检索现有属性并确定候选对象**
   - 先检索当前项目的属性标准库、设备物模型、历史兼容字段和同一协议的相关字段，判断是否已有语义、对象、统计口径和适用范围一致的属性。
   - 优先复用已有属性标识符；只有现有字段无法覆盖且协议证据支持新增属性时，才生成新标识符。
   - 控制物模型中的标识符只能作为交叉参考，不得直接当作属性标识符复用；必须重新核对属性的读写方式、数据含义和业务用途。

2. **读取并交叉验证协议证据**
   - 至少核对设备类型或产品范围、寄存器地址、字段名称、bit 位或位宽、数据类型、端序、倍率、单位、读写能力、枚举值和协议描述。
   - BMS1/BMS2、端口、簇号、相别等对象范围必须以寄存器地址、协议分组和字段定义判断，不仅依据中文名称、菜单位置或历史命名推断。
   - 同一寄存器被多个字段复用时，结合 bit 位、位宽、解析表达式和业务场景区分属性；不能仅凭寄存器地址一致就合并字段。
   - 协议原文、现有表格和研发字段存在冲突时，保留冲突证据，在备注中说明，不得静默覆盖已有口径。

3. **判定标准数据类型**
   - 数值本身具有连续或离散整数含义、且不是固定枚举或多 bit 位图时，使用 `Integer`。
   - 数值只能从有限枚举值中取值时，使用 `Enum<Integer>`，并在数据范围/枚举中逐项记录数值和含义。
   - 一个字段承载多个独立 bit 状态时，使用 `Bitmap`，记录 bit 位、有效值和含义；不得把完整位图误写成单一 Boolean。
   - 只有协议明确表示单一二值状态，且平台属性语义也按布尔值承载时，才使用 `Boolean`；“标识位”“开关位”本身不足以证明应使用 Boolean。
   - 数据类型、单位、倍率或枚举无法从协议和现有项目规范唯一确定时，标记为“待确认”，不得用猜测值写入最终口径。

4. **写回属性大表**
   - 证据能够唯一确定属性语义、标识符、设备范围、数据类型、单位、读写方式和来源映射，且已获得写回授权时，直接写入项目属性标准大表。
   - 写入时同步保存来源文件、sheet、行号或寄存器地址、原始字段名、协议版本和判断依据；项目存在变更记录时同步追加变更记录。
   - 已确认的历史属性不因新协议自动改名；新协议仅补充同义来源、来源映射或兼容说明。
   - 写回后必须回读检查标识符唯一性、字段值、表头、表格范围、来源追溯和变更记录，并报告实际写入结果。

5. **处理证据不足或冲突**
   - 缺少寄存器、只有字段名称、协议枚举不完整、设备范围冲突、同义字段无法区分，或不同来源给出不同类型时，保持“待确认”并列出具体缺口。
   - 未确认前可以输出候选标识符和判断依据，但不得把候选项标记为已确认，不得写入正式属性库的最终口径。
   - 只向需求提出人询问会改变标识符、类型、单位、枚举、设备范围或写回位置的关键问题，不重复询问已有协议已明确的信息。

### 固定词汇清单

- 定义控制 key 时，优先匹配本清单中的固定词汇，不为同一业务概念重复创建同义词或随意更换表达。
- “加热”统一使用 `Heat`，不使用 `Heating`、`Warm` 或其他替代表达。
- “开关”统一使用 `Enable`；该规则优先于来源字段中的 `Switch`、`En` 等写法。
- 固定词汇清单中没有对应词汇时，先提出候选英文词和适用范围，向需求提出人确认；未确认前不得将新词作为统一规范使用。
- 新词经确认后，才可补充到本清单，并用于后续控制 key 定义。
- 先使用英文全称组合标识符；标识符总长度不超过 30 个字符时，优先保留英文全称。
- 标识符总长度超过 30 个字符时，必须使用原子词汇库中已确认的缩写将最终标识符压缩至 30 个字符以内；不得仅因单个原子词较短就禁止缩写。
- 超长标识符允许同时缩写多个中间原子词。优先保留首段控制对象或领域词、路别或阶段编号，以及末尾的功能类型或参数类型，例如 `Bat`、`Vrt`、`Stage1`、`Enable`、`Mode`、`Time`、`Voltage`。
- 原子词汇库中的词汇应同时登记中文含义、英文全称和标准缩写。完整写法是默认表达，标准缩写用于标识符超长时的压缩；没有已确认缩写的原子词不得自行截断。
- 缩写优先采用行业通用缩写；没有行业缩写时，候选缩写必须语义明确、可唯一还原为已登记的英文全称，并经需求提出人确认。一般不使用少于 3 个字符的普通缩写，行业缩写、技术符号和数字表达除外。
- 每个缩写还应登记适用范围和歧义风险；与其他原子词缩写冲突或无法唯一还原时不得使用。
- 如果应用已确认缩写后仍超过 30 个字符，标记为“待确认”，不得继续任意删减字符。
- 长度按最终标识符的实际字符数计算；数字和字母均计为 1 个字符。
- 缩写在 PascalCase 标识符中按已确认的项目写法转换大小写，例如 `UFRT` 使用 `Ufrt`、`OFRT` 使用 `Ofrt`，不得将缩写改写成语义不明的片段。
- 已确认的固定词汇优先级高于长度规则；后续命名优先匹配固定词汇清单。

### 标识符词性与结构规范

- 不强制所有原子词汇使用动词；根据标识符表达的是动作命令、功能使能、参数还是模式，选择对应词性和结构。
- **动作按钮**使用动词开头，结构为“动作动词 + 控制对象”，例如 `StartFastCharge`、`StopFastCharge`。
- **使能开关**使用“功能名词短语 + `Enable`”，例如 `Bat1HeatEnable`、`DischargeSOCProtectionEnable`。表示被启用的保护能力时使用名词 `Protection`，不使用动词 `Protect` 与 `Enable` 直接组合。
- **参数设置**使用名词结构，结构为“对象或场景 + 限定词 + 参数名词”，例如 `Bat2MaxChargeVoltage`、`FastChargePowerPercent`、`FastChargeCutoffSOC`。
- **模式类功能**使用功能名词短语并以 `Mode` 结尾，例如 `BatHeatMode`。
- 不为追求动词形式破坏英文语法。只有标识符本身表示立即执行的动作时才使用动作动词；功能、能力、参数、状态和模式使用相应名词。

## 工作流程

1. 确认业务场景和提示词承载位置，例如系统提示词、工具描述、表格字段或页面配置。
2. 识别结构化字段已经表达的内容，确定提示词真正需要补充的业务语义。
3. 根据对应场景规范起草提示词；没有专用规范时，围绕意图、输入转换、约束、异常和结果设计最小充分内容。
4. 用一个或两个具有代表性的样例与用户确认措辞和长度。
5. 对普通提示词或未授权的属性写回，获得确认后再批量生成或写回；对已明确授权且寄存器证据充分的属性写回，按“寄存器原始协议判定与写回流程”执行。
6. 写回后检查一致性、歧义、重复、来源追溯和越权表述。

## 场景规范

- 编写或检查 IOT、储能、逆变器及其他设备控制功能提示词时，必须阅读并遵循 [控制功能提示词规范](references/控制功能提示词规范.md)。
- 编写或检查 IOT 属性物模型字段查询提示词时，必须阅读并遵循 [属性物模型提示词规范](references/属性物模型提示词规范.md)。
- 后续新增其他提示词类型时，为该类型增加独立的 `references/` 文件，并在此处补充清晰的触发条件。不要把所有场景规则堆入入口文件。

## 交付要求

- 用户只要求候选文本时，不直接修改文件。
- 用户要求写回表格或配置时，默认先确认样例和目标范围；如果需求提出人已明确授权根据寄存器原始协议自行判断并写回属性大表，则按“寄存器原始协议判定与写回流程”执行，不重复要求逐条确认。
- 检查结果应指出具体歧义、缺失规则或重复内容，并给出可直接替换的文本。
