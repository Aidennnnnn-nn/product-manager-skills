# 原型绘制、UI 与交互工作标准

本 Skill 是个人原型绘制标准的 `V1.0`。首版基线来自已验证的 Web 业务后台 UI、交互和 HTML -> Figma 工作流；Web 框架的选用按下文“Web 框架选择”执行，其他 UI 与交互细节以用户确认和目标项目最新规范为准。

本 Skill 不把单一业务的字段、权限、对象模型或业务结果写成通用原型规则；这些内容默认来自已确认 PRD。用户明确要求原型先行或跳过线框时，按当前范围执行，以用户已确认语义为依据，确认后补齐 PRD，不补造未知业务规则。

进入具体项目后，原型执行优先级为：用户当前明确要求 > 项目已确认规范 > 本 Skill 的跨项目通用标准 > 历史原型与未确认方案。项目品牌、专用尺寸、业务文案和设计系统继续由项目规范定义；历史原型中与当前规则不一致的做法不作为默认依据。

本 Skill 是用户当前 UI 与原型绘制工作的唯一个人执行标准。默认不加载或叠加其他个人、团队或第三方 UI Skill；其他 Skill 仅在用户对当前任务明确指定时作为补充参考，且不能覆盖本 Skill、项目已确认规范和用户最新要求。

## 静态页面原型模式

静态页面原型是以页面状态为单位的 HTML 视觉评审稿。为方便演示，可实现下拉选择、列表左右拖拽、页面上下滚动等轻量局部操作；这些操作只用于展示，不持久化数据、不执行真实业务处理。静态模式不实现复杂的多步骤联动、真实字段校验、接口调用、通知发送、数据写入或外部系统操作。用户未指定原型类型时，直接提出“绘制原型/输出页面”默认按静态原型处理；明确要求“线框图”时只输出线框图，不生成 HTML；明确要求可交互原型时，改用下文的交互基线。

静态 HTML 起稿时读取 [HTML 原型模板与页面框架](references/HTML原型模板与页面框架.md) 和 [标准后台原型参考](references/标准后台原型参考.html)，并可对照[默认状态预览](references/标准后台原型参考_默认状态预览.png)。前者约束多屏评审结构，后者提供可直接打开的 `1440 × 900` Light 后台壳层、筛选列表、分页、状态、抽屉、弹窗和反馈的实现参考。优先复用参考文件的 DOM 层级、空间 Token、控件组合和状态入口；按已确认需求删减或组合区块，不另造一套重复壳层。交互原型不套用静态评审画布模板。

静态原型的确认链路为：

```text
聊天框内输出页面结构与分支线框图
  -> 用户在聊天中确认线框
  -> 单文件多屏静态 HTML
  -> 用户确认静态 HTML
  -> 用户另行确认后，才升级为可交互原型或写入 Figma
```

线框图只在当前聊天框内输出，可使用 Markdown、ASCII、表格或简化框图表达页面区块、页面顺序、并行分支和关键状态；不创建 HTML、图片、附件或独立文件，也不写入 PRD 和 Figma。线框图确认不等同于 HTML 确认，HTML 确认不等同于 Figma 写入授权。静态原型表达已确认需求，不自行成为业务规则来源；未确认的字段、默认值、规则、权限和异常语义保留在 PRD 或交付说明的待确认项，不补造为产品行为。局部修改只处理受影响内容，不重新执行无关步骤；用户明确要求跳过环节时，注明本次采用的链路。

### 0.1 线框确认的固定表达

聊天框内的线框至少表达以下元素，顺序固定为“画布区域 -> 场景卡 -> 屏头 -> 需求描述区（如有） -> 应用界面/组件本体 -> 箭头与流转说明”：

- **画布区域**：标出系统/模块/功能、静态原型标题和多屏排布方式；页头不放屏号列表或图例。
- **场景卡**：标出屏号、屏标题、单句场景说明和屏内内容边界。
- **需求描述区**：默认省略；用户或项目明确要求时，放在场景卡屏头之后、应用界面之前，只写 1-3 句核心交互逻辑，不写详细需求。
- **应用界面/组件本体**：完整页面按页面壳层表达；抽屉、弹窗、Toast 等非整页内容只画组件本体，不画蒙层或蒙层下页面。
- **箭头**：用 `触发动作 + 条件/分支 + 结果` 说明流转；箭头只连接真实先后关系，不把并列对照误画成流程。

线框示例：

```text
┌────────────────────────────── 画布：系统 / 用户管理 / 成员 ──────────────────────────────┐
│ 用户管理静态原型                                                                        │
│                                                                                         │
│ ┌─ 页面 1a · 成员列表 ───────────────┐      点击「新增成员」· 有新增权限                │
│ │ 场景：首次打开成员列表              │ ───────────────────────────────▶               │
│ │ 需求描述（可省略）：管理员从列表进入新增成员，提交后按处理结果进入成功或失败。        │      ┌─ 页面 1b · 新增成员抽屉 ───────┐
│ │ [页签][筛选区][成员表格][分页]       │      点击「提交」· 校验通过 → 展示成功结果       │      │ 标题：新增成员                     │
│ └────────────────────────────────────┘                                              │      │ [字段][字段][提交]                 │
│                                                                                       │      │ [取消]                              │
│                                                                                       │      └──────────────────────────────────┘
│                                                                                         │
│ 并列分支：提交成功 1c ───────────────┐     提交失败 1d ───────────────┐                  │
│                                     ▼                                  ▼                  │
│                         ┌─ Toast 成功 ─┐                    ┌─ 失败结果 ───────┐         │
│                         │ 成员已创建   │                    │ 创建失败          │         │
│                         └──────────────┘                    └────────────────────┘         │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

示例仅表达已确认的成功与失败分支，不据此新增重试等操作。示例中的 `1a -> 1b` 是真实操作流转；`1c` 与 `1d` 是同一次提交后的互斥结果，因此横向并列。若只需要展示两个弹窗或两个抽屉对照，不存在先后操作时，应并排放置且不画箭头。

### 1. 静态交付形态

- 一个 HTML 文件承载同一场景的多屏，多个屏以场景卡并列展示；合并文件不等于合并屏。
- 一屏只表达一个页面状态或一组明确的并列分支；同一组并列分支可以并排放置两个完整页面、两个弹窗或两个抽屉，但不得把无关的两个场景叠放在一屏内。
- 上一页、下一页、屏号跳转或场景选择仅用于评审查看，不表达产品交互，也不改变业务状态。
- 静态屏至少覆盖入口、首次打开的抽屉/弹窗/表单、需求明确的分支，以及被点名的处理中、成功、失败、重试、待激活或返回状态。
- 批量导入的静态评审稿按下文“首版交互基线”第 3 节分解屏级状态；不因章节位置而把四屏评审稿误做成完整可操作的导入程序。

### 2. 画布、场景卡与屏内壳层

静态多屏评审稿使用独立的评审画布，不把固定的产品设计画布当作外层容器：

- 外层画布居中，宽度固定为 `2240px`（静态评审板不做自适应，窗口不足时页面横向滚动，拖动滚动条不会改变屏内布局与箭头位置），底部留白约 `72px`，背景使用浅灰色（默认 `#F3F5F7`）；不得使用 `min(2240px, 100% - Npx)`、百分比宽度或 `@media` 断点。
- 画布页头包含“系统 / 模块 / 功能”面包屑和 `XX静态原型`标题；页头不放屏号列表或图例，默认不另加图例；项目明确要求时按项目规范放置。该规则约束新增或本次要求修改的内容，不自动回改已确认历史原型。
- 一屏一卡，屏信息包裹页面：场景卡白底、`1px` 描边、`14px` 圆角、轻投影、`overflow: hidden`；卡头是屏信息区（屏号 + 短标题 + 入口说明，浅灰底 + `1px` 分隔线，高约 `70px`），卡体是应用界面本体。应用界面去掉自身的描边、圆角、阴影和底色，直接铺满卡头以下区域，不再用“白色信息条 + 白色页面卡”两层白块叠加。
- 同一行并排的屏卡整行等高（`align-items: stretch`），卡头因此齐平、底边也齐平；不使用底对齐（会让较矮屏的卡头下沉），也不为消掉留白而拉伸页面内容——较矮屏在框内保留自身留白，读起来是页面自身的空白。
- 需求描述区域不属于应用页面，默认不展示；仅项目或用户明确要求时，才放在场景卡屏头或画布元信息中。内容只概括本组页面的核心交互逻辑，控制为 `1-3` 句，最多说明“触发动作 -> 页面/组件变化 -> 分支结果或下一步”；不展开字段明细、业务规则、权限、接口、数据处理、实现备注或完整异常说明。
- 业务后台项目的应用界面固定 `1440 × 900`（宽 × 最小高），不按卡宽缩放；其他终端按项目已确认尺寸。项目存在已确认公共壳层时，静态稿必须直接复用该壳层的 DOM 层级、尺寸、菜单、图标、状态和交互，不得依据本 Skill 的摘要重新绘制；项目没有框架事实源时，才使用下文 V1 默认 Web 业务后台框架。
- 存在真实系统（可访问链接、截图、录屏）时，先按 [真实系统还原规范](references/真实系统还原规范.md) 出元素对照清单再绘制；结构、图标、统计口径和文案照真实写，不凭印象简化。
- 屏内结构按“顶栏 -> 左侧导航 -> 页签 -> 面包屑 -> 页面标题 -> 筛选/工具区 -> 主内容 -> 分页/弹窗/抽屉”组织；无对应区域时删除，不用空占位。
- 2 屏默认 2 列，3 屏默认 3 列，4 屏默认 2×2；并列分支同排横向展示，只有真实先后依赖才纵向串联。
- 在窄屏下可收缩间距和内边距，但不得隐藏字段、改变屏序或改变信息层级。

### 2.1 不同场景的尺寸约束

静态原型尺寸用于保证评审时的可读性和信息密度，不等同于产品最终开发尺寸；项目已确认的设备尺寸和组件 Token 优先。尺寸不足以承载真实字段时，应拆屏，不得通过缩小字号或压缩控件解决。

| 场景 | 排布约束 | 内容宽度约束 | 高度约束 |
| --- | --- | --- | --- |
| 单个完整页面 | 单列展示一个应用界面 | 业务后台固定 `1440px`；不得使用 `1180`、`1050`、`2040` 等自造宽度 | 固定 `900px` 最小高度；内容超出时增高，不压字号 |
| 一屏两个完整页面 | 仅用于同一步骤的并列分支或对照；两页横向并列 | 每页建议 `520-720px`，间距 `24-32px`；总内容宽度建议不低于 `1064px` | 两页使用相同卡内高度，取内容较高者；最小约 `650px` |
| 单个抽屉/弹窗 | 只展示组件本体，不展示页面壳层或蒙层 | 抽屉建议 `420-560px`；弹窗建议 `360-520px` | 按标题、内容和操作区计算，四周保留至少 `24px` 留白 |
| 一屏两个抽屉/弹窗 | 仅用于同一步骤的并列结果、不同权限或不同分支；横向并列 | 每个组件按单体宽度约束，组件间距 `24-32px`；总内容宽度建议不低于 `744px` | 两个组件高度取较高者，不为对齐而拉伸空白区域 |
| 完整页面 + 非整页组件 | 仅用于同一场景下的页面与结果对照，不表达蒙层叠加 | 完整页面建议 `760-1000px`，组件建议 `360-520px`，总内容宽度建议不低于 `1144px` | 页面与组件按各自内容确定；组件不得被压缩到不可读 |
| Toast/结果反馈 | 单独作为结果屏展示 | 建议 `360-560px` | 只保留提示本体和必要留白，不补画背景页面 |

一屏两个完整页面或两个弹窗/抽屉时，必须在屏标题、场景说明或箭头标签中写明两者的分支关系；如果两者需要不同的用户操作顺序，拆成不同屏。

### 3. 屏号与屏头

- 屏号使用“数字 + 小写字母”，例如 `1a`、`1b`、`2a`；数字表示功能或步骤分组，组号从 `1` 开始、不出现 `0` 组，字母从 `a` 起按组内顺序连续。先后或并列关系以真实流转为准，不仅凭编号判断。
- 屏号保持稳定且不重复；新增屏按原有分组追加未占用编号，不为追求连续而重排既有屏号。确需重排时，只修改当前可修改版本，保留冻结版本并提供新旧编号对照。
- 每屏保留屏号、短屏标题和简短场景说明。场景说明交代入口、触发条件和必要状态差异，例如“入口：1a 成员列表；点击新增成员”；菜单或外部入口写明来源。共享入口可统一标注，避免逐屏重复；不为凑成一行而删掉关键条件。

屏号、屏名和屏间入口关系以原型场景卡为维护源；交付说明的屏清单据此汇总，PRD 只按需引用局部屏号。画布页头不放屏号列表；箭头目标、评审导航和交付说明可引用屏号，不另建独立维护的清单。

### 3.1 箭头与流转说明

- 箭头用于表达页面、组件或状态之间的流转关系；静态原型中不执行真实点击、提交或跳转。
- 每条跨屏箭头必须配一条独立的触发说明，至少写清“触发动作 + 条件/分支 + 结果”。推荐格式：`点击「按钮」· 满足条件 → 打开/进入/展示「目标状态」`。
- 示例：`点击「添加下级组织」· 已选择上级组织 → 打开「添加下级组织」抽屉`；`点击「查询」· 组织代码不存在 → 展示代码错误提示`。
- 主流程使用实线箭头；同排相邻的先后状态可水平连接，跨行依赖纵向串联；互斥分支从同一节点分叉并横向排列。分支宽度按内容与可读性确定，不固定比例。箭头方向、标签和目标屏必须一一对应。
- 箭头标签只解释流转逻辑，不写实现备注、接口名称或需求编号；业务规则和异常处理仍以 PRD 为准。
- 没有真实流转关系的两个页面不得用箭头连接；仅用于对照时使用“并列对照”场景说明，不伪造流程。
- 静态原型用连接器表达真实跨屏流转，不用纯文字流转框或悬空小箭头：同排相邻的先后状态可水平直连，跨行流转用曲线连接；起点圆点压在来源卡边框上，终点实心三角顶在目标卡边框上，触发说明钉在连线上。并列页签、同屏对照不画流程箭头。分叉、合流、交叉各配一条说明，不把多个目标合并成一句话。
- 跨行曲线按整板绝对坐标绘制：`.flow` 容器 `position: relative; width: 2240px`，内含 `svg.flow-curves` 与对应的 `.flow-note`；卡片中心依据实际布局测量，不套用固定列坐标。起点与终点必须压在真实卡边框上，画布或卡片尺寸变化后重新校准，不凭容器高度推算端点。同排直线同样要贴合两侧卡边框，标签不得遮挡屏内内容。
- 跨行走线以“竖直引出 → 曲线斜移 → 竖直落入”为默认形态；同排直线按真实方向落入。调整连线带高度时同步容器高度、SVG `viewBox` 与路径终点，避免箭头悬空、穿过卡片或压住页签说明。
- 流转说明只写“触发动作 + 条件 → 结果”，不写屏号（如 `3a → 3b`）；落点取曲线参数位置：单线与分叉取 `t=0.5`，交叉两条各取靠起点侧的 `t=0.25`，合流取汇合后主干 `t≈0.35`，并保证说明中心距上一行卡底不小于 `32px`，避免长尾段的中点落进上方卡片。
- 同屏两个页签（如成功页签 / 失败页签）或同一屏的口径对照属于并列，不画箭头；在屏头写明“X 的失败页签”或“并列对照”，不伪造先后。
- 说明只写触发动作、条件与结果；不写示例数量、批次统计、数据样例、实现备注或需求编号。
- 连接器优先连接相邻同排或紧邻上下行的屏。来源与目标不相邻（隔行、旁支回流）时不得硬画线：改为在来源行底部加一行“↘ 见下屏 2b”或右对齐的回退注 `↩ …`，避免线条指向空白或穿过中间卡片。
- 并排只用于“同源变体”：同屏页签用 `⇄`、无先后的并列用 `∥`、有先后的两态用横向箭头；每处并排必须在其上方加一条组标签（浅底胶囊 + 12px 灰字），写明关系，例如 `同屏页签 · 解析结果（成功 / 失败）`、`顺序 · 创建中 → 失败重试`、`同源失败 · 分块元数据 / 向量化存储`。来源不同、也没有先后关系的两屏不得并排。
- 回退与循环不单独占行，统一写成所在行下方的右对齐小字：`↩ 4c 重试结束回 4a 继续；4e 重试回 4a`，随卡片走，不夹在箭头与下一屏之间。
- 一行内出现两张并列卡时，连接器分别对准两张卡的中心（`543 / 1697`），合流写两条汇入线，分叉写两条分出线；交叉时两条线各落到自己的目标卡，不图省事画成一条居中箭头。

需求描述与箭头标签应保持同一粒度：只说明用户动作、页面/组件状态变化、分支条件和结果。例如：“管理员点击「新增用户」，打开新增用户抽屉；提交后按处理结果进入成功或失败状态。” 不应写成字段清单、规则表或技术处理说明。

### 4. 页面文案白名单

区分产品界面与评审注释：

- 产品界面保留真实菜单、标题、字段、按钮、状态、提示及校验文案。已确认的字段帮助、格式说明、风险提醒和必要操作引导正常保留，表达简洁，不复制整段 PRD。
- 场景卡屏头、入口和箭头说明属于评审注释，放在产品界面之外，只解释场景与流转。
- 产品界面和可见评审注释不放内部需求编号、章节引用、实现备注或“待确认”标签；必要追踪信息放在 PRD、交付说明或非展示元数据中。
- 不在产品界面或评审注释中写字号、颜色、尺寸、圆角等视觉规格说明；HTML/CSS 和规范文件中的正常定义不受此限。状态说明使用不可操作、隐藏、仅展示、阻止提交等可判断行为，视觉样式不代替行为定义。

### 5. 弹窗、抽屉与反馈屏

- 弹窗或抽屉等非整页内容只绘制对应组件本体，不展示蒙层区域、蒙层下的页面内容或用于衬托的背景区域；组件外只保留必要的评审画布留白。
- 抽屉包含标题区、可滚动内容区和底部操作区；标题只写动作名，不追加流程说明。字段级主操作放在对应字段下方，底部默认只保留取消、返回等次要操作。
- 确认型弹窗包含动作标题、简短确认文案及需求规定的取消/确认操作，主操作位于右侧。信息、表单、进度和结果类弹窗按对应场景设计，不套用确认型结构；是否二次确认遵循已确认需求，不自行增删。
- Toast/结果反馈只绘制提示本体并居中展示，不铺底层页面；成功、失败、处理中分别使用独立屏，不合并成一屏。
- 保存、确认等操作未在 PRD 或项目规范中指定更具体反馈文案时，成功与失败状态默认分别使用“操作成功”和“操作失败”；已有明确业务结果文案或特殊反馈要求时遵循已确认内容。
- 处理中与失败屏按已确认需求展示反馈和允许的操作。是否允许取消、关闭、重试及其恢复路径以 PRD 为准；规则缺失时提出待确认项，不默认添加重试，也不统一删除已确认的操作。

### 6. 列表、筛选与状态表达

- 静态列表的行操作默认直接展开为文字按钮（常用信息色可使用 `#1677FF`），具体动作由 PRD 和项目词表决定；状态与操作互斥，例如启用中只展示“停用”，停用中只展示“启用”。
- 不可用操作按 PRD 区分隐藏、仅展示或不可操作，不默认互换；状态用可判断的文字或其他明确线索辅助表达，不得只依赖颜色。
- 表格结构保持稳定：表头、数据行、分页和空状态的高度与对齐在同一组屏内一致。可参考表头约 `40px`、数据行约 `62px`、分页左右分列的组合，但项目组件规则优先。
- 筛选区采用“标签在上、控件在下”的栅格；控件默认 `40px` 高、`12px` 圆角；查询在左、重置在右；输入型筛选占位为“请输入”，选择型空值按语义使用“全部”或“请选择”，不重复字段名。

### 7. 状态子集与省略说明

只绘制本次需求涉及的已确认状态，不主动铺开空、无权限、极值、长文案等全集。视觉相似但会影响用户判断、可执行动作、恢复路径或下一状态的场景应清楚区分，必要时分别建屏；悬停、聚焦等控件状态不因此各建静态屏。多个可能结果同排，有先后依赖时纵向串联。已确认但遗漏的关键状态应补齐，业务规则缺失时提出待确认项。交付说明记录影响本次闭环的省略项及原因，不罗列所有无关状态。

### 8. PRD 咬合与文件归档

- 业务入口、字段、按钮和状态含义以已确认 PRD 为准；屏号、屏名和屏间对应关系由原型维护，PRD 可按需引用，不强制一一列出所有屏。
- 与界面有关的需求规则应能定位到页面或状态，原型中的业务字段、动作和状态应有需求依据；允许用名称、局部屏号或非展示元数据追踪，不强制逐字段建矩阵，非界面需求不强制映射到屏。
- PRD 记录原型模式和文件链接，交付说明从场景卡汇总屏清单及用途。用户明确要求原型先行时，在原型确认后于当前可修改阶段补齐 PRD 的需求、规则与验收，不只补链接，不回写冻结阶段。
- 静态原型文件优先使用中文命名，建议格式为 `<系统>_<模块>_<场景>静态原型_V1.0_<YYYY-MM-DD>.html`；通常与对应 PRD 放在同一目录，以保证相对链接有效。
- 修改前按 `product-work-standards` 的评审阶段与产品版本冻结规则确认可修改副本；项目要求备份时先备份。新阶段或新版在新副本中修订，不覆盖历史 HTML、附件或 Figma 节点。发现孤立素材只报告，不自动删除。交付说明汇总屏清单、用途、差异及影响闭环的省略项；涉及术语迁移或重编号时列出必要的新旧对照，普通局部修改不强制建对照表。

### 9. 静态原型交付自检

- 屏号稳定且不重复，场景卡与交付说明汇总一致，PRD 不另维护完整屏清单；入口与流转明确，并列分支同排，先后顺序正确；画布页头没有屏号列表。
- 页面无空白、重叠、裁切、文字溢出、异常滚动条或布局跳动；字体、颜色、图标和真实业务文案加载正常。
- 连接器端点实测贴合：圆点压在来源卡底边、三角顶点顶在目标卡顶边，偏差为 `0`；流转说明骑在曲线上且不压卡、不互压；没有连线穿入卡片。测量与截图方法按 [HTML 原型模板与页面框架](references/HTML原型模板与页面框架.md) 的“绘制与验证技巧”执行。
- 产品界面与评审注释分离，真实帮助和校验提示保留；没有内部需求编号、章节引用、实现备注或视觉规格说明；弹窗/抽屉没有蒙层下内容，Toast 只保留提示本体；确认、处理中与失败操作符合已确认需求。
- 保存、确认等操作的成功/失败反馈符合默认文案规则；如使用更具体文案，应能追溯到 PRD 或项目规范。
- 操作列展开规则、状态与操作互斥规则、禁用表现和筛选控件文案符合 PRD 与项目规范。
- 交付前运行 `node scripts/audit.mjs <原型.html>`：横向溢出、`app` 宽度、弹窗宽度、重复 id、屏号连续性和内联脚本语法必须全部通过；其余项按本节人工核对。
- 交付说明分别记录静态检查、浏览器打开/截图回读、人工视觉确认和用户确认结果，不把静态原型自检称为研发测试。

## 流程图绘制边界

- 产品原型中的业务流程图、页面流程图、用户操作流程图和 PRD 配套流程图，默认使用本 Skill 的 HTML-first 工作流，直接以 HTML/CSS/SVG 或项目现有原生图形结构绘制，并与对应原型页面保持同一事实源。
- 以上产品流程图默认不调用 `archify`，不生成 Archify 专用 JSON、独立 Archify Viewer 或 Archify 交付物；流程节点、分支、异常、状态和说明应在 HTML 原型中表达。
- 只有用户明确要求“技术架构图”“基础设施拓扑”“API 时序图”“数据管道图”等独立技术图，并明确指定使用 `archify` 时，才允许切换到 Archify；用户未指定时继续使用 HTML/CSS/SVG 原生绘制。
- 项目已有流程图 HTML 时，优先在原文件中做最小范围修改；不得因为流程图需要校验而自动切换到 Archify 生成链路。

本 Skill 按可公开阅读、可跨项目安装和可独立理解的方式维护，不写入公司或项目专属路径、私有链接、访问凭据、敏感数据或未脱敏业务样例。只有用户明确指定时，才升级版本、创建版本 Tag 或发布新的 GitHub Release。

## Web 框架选择

- 当前个人原型标准的 Web 框架候选只有本 Skill 定义的 **V1 默认 Web 业务后台框架**。绘制 Web 端页面时，默认采用其公共壳层和页面层级，不自行拼接第二套框架。
- 框架的具体结构和尺寸以本 Skill 的“页面画布与壳层”为依据；进入具体项目时仍须读取项目文件的当前版本，不仅依赖本 Skill 摘要。
- 跨项目复用的是页面框架，不自动带入来源项目的品牌、平台名称、菜单、业务对象、权限或专用文案。目标项目已确认的框架优先于个人默认框架；只有项目事实源不清或彼此冲突时才确认，不对已明确的优先级重复提问。
- 后续需要其他 Web 框架时，先明确来源、适用场景和与现有框架的选择条件，经用户确认后再扩展候选；未确认前仍只有上述一个候选。

### 项目框架锁定与复用

进入已有公共框架的项目后，先定位项目指定的唯一工作入口和已确认框架原型，再开始绘制业务页面。框架复用采用以下硬性规则：

1. 把顶部栏、品牌区、左侧导航、平台入口、功能页签、全局工具、个人菜单、工作区偏移和公共弹层视为锁定壳层；除非当前需求明确修改全局框架，否则不得删减、改序、改尺寸、换图标或重写交互。
2. 业务原型只替换项目框架声明的业务内容槽，并按已确认信息架构设置当前平台、菜单选中态、页签、面包屑、页面标题和业务内容；不得复制一个近似壳层后自行调整。
3. 同一项目的静态原型、可交互原型和后续 Figma 必须来自同一框架事实源。历史页面与当前框架冲突时，以项目指定的当前入口为准，不从多个历史文件拼接。
4. 项目框架未提供可复用代码时，先从确认稿提取稳定结构和 Token，形成当前原型内的单一壳层组件，再由所有场景复用；不得为每一屏重复手写不同的顶部栏或菜单。
5. 组件本体评审不携带页面壳层；完整页面评审必须携带完整锁定壳层。不能为了节省画布而缩写菜单、隐藏顶部工具或改变导航宽度。
6. 交付前对框架事实源与输出稿做结构差异检查，至少核对顶部工具数量与顺序、菜单名称与顺序、导航展开/收起宽度、功能页签高度、工作区偏移、面包屑层级和页面标题位置。存在非本次需求导致的差异时不得交付。

## 首版 UI 基线（V1）

以下规则作为当前个人原型 Skill 的首版可复用基线，默认适用于可交互原型和实际产品页面。静态多屏评审画布、场景卡、屏内壳层和非整页组件遵循上文静态模式，不把本节的产品画布尺寸当作静态评审稿默认值。Web 框架的选用遵循上节；进入具体项目时，必须先读取项目 UI 规范全文，并以已确认的项目规范为准。

绘制或修改页面布局、控件、状态和交互时，读取 [控件与空间规范](references/控件与空间规范.md)。该参考统一约束静态原型与可交互原型的空间层级、控件结构和适用状态；项目已有明确设计系统时，以项目规范为视觉事实源，同时保留本 Skill 的语义、交互和验收要求。

### 1. 页面画布与壳层

- 业务后台默认使用 `1440 x 900px`、Light 主题。
- 顶部栏高度 `48px`；左侧导航收起宽度 `60px`，展开宽度 `220px`；工作区背景 `#F8F8F8`；内容面板白色、圆角 `12px`。
- 页面层级按“顶部栏 -> 左侧导航 -> 产品/模块导航 -> 面包屑 -> 页面标题 -> 页签或筛选 -> 主内容 -> 分页/抽屉/弹窗”组织。
- 具体功能页面标题只展示菜单名称，不在标题下方添加解释性副标题；页面说明写入 PRD、全局规则或交互提示。
- 面包屑表达真实页面位置，不替代页面标题；分隔符使用 `chevron-right`，当前页面使用 `aria-current="page"`，容器使用 `aria-label="页面路径"`。
- 页面空间按“画布与壳层 -> 页面区块 -> 容器 -> 字段或控件组 -> 控件内部”分层设置。先确定层级再选择间距，不用零散像素值修补布局。
- 同一层级使用一致的间距档位；相邻元素的业务关系越强，间距越小。标题与所属内容、字段标签与控件、错误信息与对应字段必须保持清楚的归属关系。
- 页面、弹窗、抽屉、筛选区、表单和操作区的推荐空间组合见 [控件与空间规范](references/控件与空间规范.md)。项目未规定时使用其中的默认档位，不自行产生 `13px`、`17px` 等临时间距。

### 2. 视觉与组件基线

- 使用 `4px` 基础网格，常用空间档位为 `4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64px`；具体选择按页面、容器、组件和组件内部层级执行。
- 中文优先使用 `PingFang SC`，英文和数字优先使用 `Poppins`；通用字体栈为 `Poppins, "PingFang SC", "Microsoft YaHei", sans-serif`。
- 页面标题通常为 `20px / 28px`；模块标题 `16px`；正文和控件 `14px`；辅助信息 `12px`。
- 业务按钮默认高度 `36px`、圆角 `12px`；输入框和选择器默认高度 `40px`、圆角 `12px`。
- Web Radio 和 Checkbox 默认 `16 x 16px`；列表操作图标使用 `20 x 20px` 画布。
- Button、Input、Select、Textarea、Radio、Checkbox、Switch、Tabs、分页、菜单、Tooltip、弹窗、抽屉、Toast、状态标签、上传、加载和进度等常用控件，按 [控件与空间规范](references/控件与空间规范.md) 选择类型、结构、状态和空间，不按单页临时造型。
- 列表与管理页的分页条按 [列表与分页控件](references/列表与分页控件.md) 直接取用结构、样式和脚本，不重新设计页码序列算法、每页条数归位和跳页边界；该参考末尾的验收清单作为分页部分的自检项。
- 静态与可交互原型使用同一控件结构、尺寸和空间基线。静态稿只呈现本次需要评审的状态；可交互稿在同一结构上补齐适用的操作、焦点、键盘、加载、错误和恢复行为。
- 优先复用已确认的组件、变量、Token、图标和真实图片资产；不得用整页截图替代可编辑 HTML 或 Figma 结构。
- 原型内的图标统一从 [图标库](references/图标库.md) 的 `assets/icons.js`（54 个基础 UI）与 `assets/icons-domain.js`（12 个业务语义 + 3 个组合）取用：Lucide `1.67.0`（ISC）、24 网格、`stroke-width:2`、`currentColor`；Figma 侧使用同库官方组件库并对齐版本。不得手写或临摹 SVG 路径，缺图标先改 `scripts/build-icons.mjs` 再重跑构建，不直接改产物。
- 状态不得只依赖颜色，必须同时提供文字、图标、形状或结构差异。
- 关联功能的原型应优先复用已确认的公共入口页面、列表结构、筛选字段、表头和行操作；不得为单个流程制作结构或信息密度明显不同的简化版入口页。
- 页面流程箭头统一采用“箭头图形 + 独立触发说明”结构：箭头居中，触发操作说明放在箭头下方；说明文字使用一致的辅助字号、颜色和行高，避免与箭头合并成一行。
- 多条互斥路径如果由同一个前置页面触发，应在同一行横向并列展示，并保持卡片宽度、间距、箭头和触发说明一致；不得把替代路径依次纵向串联展示。
- 同一路径存在多个可能结果时，应将结果状态在同一行横向并列展示；只有存在真实先后依赖的状态，才按时间顺序纵向串联。布局判断可归纳为：并行替代路径同一行并列、同一路径的可能结果同一行并列、有先后依赖的状态按顺序串联。

### 3. 列表与筛选

- 筛选区采用“字段标签在上、控件在下”的栅格结构，字段过多时自然换行。
- 筛选控件默认高度 `40px`、圆角 `12px`；输入占位默认“请输入”；选择控件按空值语义使用“全部”或“请选择”。
- 查询和重置位于筛选区末端，顺序为“查询”在前、“重置”在后。
- 列表页标题和主要操作处于同一视觉层级；表头、数据行、分页和空状态保持稳定结构。
- 列表页的区块顺序、列宽四档、总宽策略、对齐和横向滚动时的操作列吸附按 [列表页装配与列宽](references/列表页装配与列宽.md) 执行；列宽不足先按该参考的压缩优先级处理，不靠缩小字号或压低行高换取空间。
- 可交互原型可按项目组件规则使用图标和 Tooltip；静态原型的列表行操作默认直接展开为文字按钮，不自动收进“更多操作”。只有 PRD 或项目规范明确要求菜单时，才使用“更多操作”。

### 4. 表单标准组件

HTML 和 Figma 原型中的输入与选择控件必须形成完整、可评审的标准组件，不得仅依赖浏览器原生样式表达完成态。项目已有设计系统时优先复用；没有已确认组件时，可参考成熟业务后台的交互模式，但颜色、尺寸、圆角和品牌表达继续由目标项目规则决定。

- Input 与 Textarea 的可交互组件按本次范围检查默认、Hover、Focus、已填写、只读、禁用和错误等适用状态；静态稿仅呈现需要评审的状态，不为每个控件状态独立建屏。浏览器原生 Focus 外框不得与项目 Focus 样式叠加形成双重描边。
- 单选 Select 使用带触发器和选项弹层的 Combobox 结构，至少支持展开/收起、当前值、选中态、禁用态、无结果、点击外部关闭、`Escape` 关闭、方向键移动和 `Enter` 选择。
- 多选 Select 使用标签或摘要回显已选值；选项使用复选语义，选择一项后弹层保持打开，支持逐项移除、全部清空、禁用项和超出可见数量后的折叠表达。
- 选项少且需要直接比较时优先使用 Radio Group；多个独立值可同时选中时使用 Checkbox Group。Radio 和 Checkbox 的标签整体可点击，并覆盖未选、选中、Focus-visible 和禁用状态；Checkbox 按业务需要支持半选。
- Select 弹层宽度不小于触发器，限制最大高度并在溢出时滚动；选中、Hover、键盘活动项和禁用项必须有稳定且不引发布局跳动的状态差异。
- 字段首次展示不主动报错；失焦或提交时校验，错误靠近字段展示，修正后即时移除，提交失败时定位到第一个错误字段。
- 对本次实现或修改的可操作控件，用鼠标和键盘检查适用的打开、选择、移除、清空、关闭、禁用与错误恢复；静态稿的局部演示只检查实际提供的操作，不能用关闭状态截图代替交互检查。
- Switch 只用于切换后立即生效的二元状态；需要填写完成后统一提交、存在三个及以上选项或需要用户比较后确认时，改用 Checkbox、Radio 或 Select。Switch 的标签整体可点击，交互版同步更新 `aria-checked`，处理中锁定重复切换并提供可观察反馈。

## 首版交互基线（V1）

以下内容主要适用于可交互原型；静态原型优先遵循上文的屏级状态子集、文案白名单和评审画布规则，不因本节自动扩展未被 PRD 点名的状态。

### 1. 状态覆盖

按本次需求检查默认、加载/处理中、空、禁用、成功、失败/错误、长文案和极值数据等适用状态，不机械展开全集。已确认但遗漏的关键状态应补齐；缺少业务依据时提出待确认项，不自行添加处理规则。行为或恢复路径不同的场景须清楚区分，静态分屏遵循上文状态子集。

页面级与容器级状态按以下三态实现，文案与按钮不另造变体：

- 加载中：默认加载效果（骨架或加载图标），保持页面结构；不配文案与按钮，不显示为“无数据”。
- 无数据：状态图标 + 标题“无数据”，居中；不加说明文案、不加任何按钮（含新建、清空筛选、重试），不弹 Toast，不把查询条件写进状态内。页面无记录、查询无命中、筛选无命中共用同一表现。
- 加载失败：状态图标 + 标题“加载失败” + 唯一按钮“重新加载”；不加副标题、错误码与第二个按钮，不自动重试、不弹 Toast，失败区不继续展示旧数据，页头、筛选区与页面级操作入口保留。

“重新加载”只用于加载类失败；操作类失败（保存、提交、删除、启停、重置密码）用 Toast 与“重试”，不进入失败态。容器内局部加载（抽屉详情、浮层列表、下拉选项）在各自容器内展示同一套状态。菜单权限缺失由全局框架拦截，不在页面内实现“暂无××权限”状态；数据范围不足按隐藏越权数据或返回空结果处理。

### 2. 表单、抽屉与弹窗

- 必填字段在离开字段或提交时校验，首次打开不主动展示空白错误。
- 用户补充有效内容后立即移除对应错误状态；提交时执行全量校验并定位到第一个错误字段。
- 字段级问题优先在字段附近提示；Toast 或页面级反馈用于系统、网络、接口超时等无法定位到字段的问题。提交校验失败时只做字段描红与就地提示，并滚动聚焦到第一个错误字段，不额外弹总提示。
- 内部流程说明、实现备注和评审解释不作为产品界面常驻文案；已确认且帮助用户完成任务的字段说明、格式要求、风险提醒与操作引导正常保留。
- 必要提示贴近触发点并保持简洁；常驻、校验时、悬停或展开后展示，以已确认场景为准，不因追求界面简洁隐藏必要信息。
- 需求中的“待确认”、实现限制和原型模拟说明不直接作为默认 UI 文案展示；应保留在 PRD、需求追踪或交互注释中，除非它本身影响用户当前决策。
- 抽屉由标题区、可滚动内容区和底部操作区组成；遮罩、焦点管理、关闭行为和操作顺序必须在 HTML 中可评审。
- 只读详情和可编辑表单要有明确视觉与结构差异，不能只用禁用输入框表达全部只读内容。
- 当主操作属于某个字段或字段组时，应放在对应字段下方；若参考页面要求居中，按钮应与字段控件同宽并保持居中。底部操作区默认只保留取消、返回等次要操作，除非需求明确要求主操作置于底部。
- 取消、确认和破坏性操作的顺序与样式应匹配已确认风险；是否二次确认、可取消、可关闭或可重试由 PRD 定义，不在原型阶段自行增删。
- 同一能力有多个入口时，按 PRD 统一默认值、回显、校验、失败处理和返回行为，明确入口差异；复杂关系使用对照表，简单关系不强制建矩阵。
- 主按钮在提交或执行期间进入加载态并阻止重复触发；不得只改变按钮文字而保留可重复点击能力。操作完成后按已确认结果恢复、关闭或进入下一状态。
- 下拉菜单、Popover、Tooltip、弹窗和抽屉必须明确触发器、打开状态、关闭路径和焦点返回位置。可交互原型至少检查点击外部或遮罩、`Escape`、关闭按钮和提交后关闭中实际适用的路径。

### 3. 批量导入

绘制静态批量导入原型时，先打开 [四屏 HTML 原型参考](references/批量导入标准交互_四屏评审原型.html)，并对照 [整板预览图](references/批量导入标准交互_四屏评审预览.png) 回读排布、弹窗结构和连线。参考文件是可运行的单文件视觉样例，优先复用其四屏状态和同批次页签关系；项目设计系统决定最终样式，业务字段与文案仍按 PRD 和项目词表替换。不要把参考文件中的示例数据、弹窗尺寸或配色当成跨项目硬规范。

PRD 已确认采用批量导入时，以“选择文件 → 上传与解析中 → 同批次解析结果”为默认原型链路。解析成功和解析失败是同一批次的两个页签，不是先后执行的两次导入；本节不替业务 PRD 确定文件格式、数量上限、字段、校验、部分导入策略或最终业务结果。

**静态评审稿：四屏展示。**

| 屏 | 状态与入口 | 必须表达的内容 |
| --- | --- | --- |
| 1a | 初始上传；从业务入口打开 | 弹层标题、操作说明、下载模板、点击或拖拽上传区；尚无结果表和确认导入。 |
| 1b | 选择文件后上传与解析中 | 上传区原位显示处理中提示，锁定关闭、重复选择、拖拽和提交，避免重复上传。 |
| 1c | 解析完成，默认进入成功页签 | 文件名、总数/成功数/失败数、可导入记录、分页、确认导入、重新上传。 |
| 1d | 从同批次结果切换到失败页签 | 保留同一文件与统计口径，列出原始行号、业务定位字段（如适用）及失败原因，提供失败记录导出和重新上传。 |

- 排布默认为 2×2：1a、1b 同排，1c、1d 同排。1a → 1b 为同排顺序，可水平直连；1b → 1c 为解析完成后的跨行流转，用曲线连接；1c 与 1d 是同一结果区的页签切换，只标注并列关系，不画先后箭头。
- 场景卡屏头说明入口与触发条件；产品弹窗只画组件本体，不叠加底层页面、蒙层或另一层白色外壳。上传、文件摘要、页签、表格、操作区沿用同一组件结构，仅替换状态差异；不为等高拉伸较短弹窗。
- 统计口径必须自洽，示例记录不得让总数与成功数、失败数矛盾。示例字段和文案仅供评审占位，实际内容以 PRD、项目词表及目标平台语言为准。
- 重新上传返回文件选择并清除上一批解析结果。确认导入后的业务动作由 PRD 定义；未确认时在交付说明标为待确认，不自动补画“正在导入”“导入成功”或“导入失败”屏。

**可交互稿：按已确认范围补齐行为。**

- 点击选择与拖拽上传走同一校验和状态转换；处理中防重复触发，结束后进入同一结果容器，成功/失败页签切换不重复解析。
- 成功页签的确认导入只提交 PRD 允许的记录；存在失败记录时是否允许部分导入或要求整批原子提交，以 PRD 为准。失败页签导出内容至少对应当前失败记录、原始行号和失败原因；其余字段由 PRD 定义。
- 如果 PRD 明确要求独立的执行中或执行结果，则在四屏基线之后追加相应状态，并区分“解析结果”与“业务导入结果”；不得把解析成功数直接写成最终导入成功数。返回、关闭、重试及结果保留规则也依 PRD 实现。
- 对已有项目规范或已确认原型存在不同导入步骤的情况，先说明差异与依据，再按当前项目已确认规则绘制，不反向修改冻结版本。

### 4. 原型回归与证据

改动原型后按以下顺序自检，并如实报告每一项结果；未执行或环境受阻要写明，不记为通过。

1. 备份：改动前把当前文件复制到项目约定位置，命名带日期与改动原因。
2. 结构与语法：确认无重复 id、无横向溢出、内联脚本可通过 `node --check`；项目已配套 `scripts/audit.mjs` 时直接运行该脚本。
3. 加载检查：用 jsdom 或浏览器真实加载，捕获脚本错误与资源缺失，运行时错误要求为 0。
4. 行为断言：针对本次改动写最小断言集（默认态、关键交互、状态切换、按钮可用性），放在临时目录，不随交付物提交；改完跑全量断言并给出“通过 X / 共 Y”的结论。
5. 视觉回读：按项目基准尺寸截图（默认 1440×900），核对本次改动的区块、状态与文案。
6. 报告口径：静态检查、浏览器交互、视觉结果与用户确认分别说明，不把截图当作行为验证，也不把原型自检表述为研发测试。

## 原型交付门禁

### 静态原型

1. 先在聊天框输出低保真线框图，等待用户确认；线框阶段不创建 HTML、图片、附件或独立文件。
2. 默认在线框确认后，按已确认 PRD 和本节规则生成单文件多屏 HTML。业务文案、动作与状态可回溯到需求；屏号由原型维护，需求编号不展示在界面或评审注释中。用户明确指定的原型先行或跳步按本次范围执行。
3. 定稿前检查文件、HTML 结构、重复 ID、链接与资源加载，并完成浏览器打开、截图及视觉回读。静态检查、浏览器检查、视觉结果和用户确认分别报告；未执行或环境受阻明确说明，不记为通过。含脚本时追加实际提供的关键点击与状态结果检查，记录运行时错误，不以截图替代行为验证。
4. 检查空间与控件一致性：间距来自统一档位，同级区块保持同一密度；按钮、字段、开关、标签页、弹层和反馈控件的类型、尺寸、状态及操作位置符合 [控件与空间规范](references/控件与空间规范.md)。
5. 静态 HTML 未经用户确认，不升级为可交互原型或写入 Figma；静态 HTML 确认也不替代 Figma 写入授权。
6. 是否同步 PRD 以业务含义判断。动作结果、权限、默认值、校验、状态转换或流程变化时，先更新当前可修改阶段 PRD 并确认受影响语义，再调整 HTML；纯排版、错别字和不改变含义的表达调整，可只更新 HTML。跨文件写入遵循本次授权，未授权部分报告待同步；任何情况均不回写冻结阶段。

### 可交互原型与 Figma

1. HTML 默认以已确认 PRD / Requirements Baseline 为依据，业务文案、状态与关键交互可回溯到需求；原型先行遵循用户明确范围及后续 PRD 补齐要求。需求编号可留在非展示追踪信息中，不显示在界面或评审注释中。
2. HTML 是交互原型的首个可评审版本，也是确认后写入 Figma 的结构和视觉事实源；HTML 未确认不进入 Figma。
3. Figma 只交付已确认 HTML 的原生可编辑结构，不在写入阶段新增业务能力或改变已确认交互。
4. 交付前实际执行本次实现或修改的关键交互，核对状态结果并检查运行时错误；通过要求是已执行范围内无未解决的原型运行时错误。分别说明静态、浏览器交互、视觉检查及用户确认结果，标明未执行或受阻项，不把原型自检表述为研发测试。
5. 对本次使用或修改的控件检查静态与交互结构一致性，并验证适用的 Hover、Focus-visible、按下、禁用、加载、错误、打开关闭、键盘操作和焦点回收；未用到的状态不为凑全集而实现。

## 核心约定

- 静态 HTML 是静态视觉评审源，可交互 HTML 是交互评审源；Figma 是已确认 HTML 的可编辑交付结果。先在 HTML 中完成结构、文案、布局、样式、响应式与关键状态，再按对应门禁同步到 Figma。
- 静态模式默认链路为：`聊天框线框 -> 单文件多屏 HTML -> 用户确认`；明确要求后才升级交互或进入 Figma。可交互模式为：`HTML -> 本地预览与调整 -> 用户确认`；仅另获 Figma 写入授权后才继续本地写入及回读，既有授权覆盖本次动作时不重复询问。
- 优先减少运行依赖；要求离线交付时，将必要资源随文件提供或内联。业务链接与资源依赖分别判断，不把零外链、特定图标函数或 SVG 写法设为所有原型的硬约束。
- 默认不调用远程 Figma MCP。优先使用本地插件、Figma 桌面端或其他本地可控路径。
- 只有用户明确要求 MCP，或本地路径不可行且用户确认切换后，才进入远程 MCP 备用路径。
- Figma 输出必须由可独立编辑的 Frame、文本、图形、组件和图片填充组成。不得用整页截图冒充可编辑原型。
- 本地交付目录和面向用户的文件优先使用中文命名；技术文件名受项目约束时沿用既有规范。
- 创建、移动、覆盖或删除本地文件前，先说明目标路径、影响和预期结果并获得确认。HTML 定稿后，写入或覆盖 Figma 前再次确认目标文件与写入范围；用户已经明确授权当前动作时无需重复询问。

## 默认流程

### 1. 静态原型流程

1. 读取项目上下文、已确认 PRD、项目 UI 规则和相关历史原型，明确本次页面、状态、屏号和非目标范围。
2. 若项目存在已确认公共框架，记录框架事实源和锁定区，只允许业务内容槽、当前菜单状态及本次需求范围内内容变化；不存在时才采用 V1 默认框架。
3. 在聊天框输出低保真线框图，说明页面区块、箭头触发逻辑、并列分支和关键状态；等待用户明确确认。
4. 线框确认后，再创建或更新单文件多屏静态 HTML；涉及本地文件时，先说明目标路径、修改范围和预期结果，遵循项目授权规则。
5. 按静态画布、场景卡、屏级尺寸、组件本体展示和文案白名单完成绘制；完整页面复用同一锁定壳层，只替换内容槽；可加入模板参考中限定的轻量演示操作，不实现复杂多步骤联动、真实业务写入或接口调用。
6. 完成静态检查、框架差异检查、浏览器打开/截图回读和人工视觉检查，交付屏号清单、每屏用途、差异和有意省略的状态。
7. 等待用户确认静态 HTML；未经单独确认，不进入可交互实现或 Figma 写入。

### 2. 可交互原型流程

1. 明确目标设备、页面状态、可复现的交互范围、目标路径和非目标范围。
2. 创建或更新 HTML，实现需求已确认的交互、校验、反馈和状态转换；不擅自新增业务规则。
3. 启动本地预览，分别完成浏览器交互检查和视觉回读。
4. 用户确认 HTML 后，若用户另行授权，再进入 Figma 写入流程。

## Figma 写入流程

### 1. 明确目标与写入范围

确认以下信息足以开工：

- 原型目标、使用场景和目标设备。
- 目标 Figma 文件 URL；有参考设计时，同时取得精确节点 URL。
- 是新增独立 Frame、更新指定节点，还是覆盖已确认范围。
- 需要表达的页面、状态、交互和关键文案。

信息不足且会改变设计方向时先提问。信息充分时给出简短执行方案、目标路径和影响范围，获得确认后继续。

### 2. 选择设计参考

需要通用设计素材时读取 [设计参考资料使用规范](references/设计参考资料使用规范.md)，选择 1-3 个匹配来源。用户提供的参考 Figma、截图、品牌规范或现有产品界面优先于通用资料。

记录实际使用的参考来源。额外来源标记为“补充来源”并说明原因，不要把浏览过但未采用的资料写进交付说明。

### 3. 创建或更新 HTML 原型

推荐位置：

```text
交付素材/<主题>_<日期>/原型预览.html
交付素材/<主题>_<日期>/原型数据.json  # 仅在结构化同步确有价值时创建
```

HTML 应是可评审的产品界面，而不是功能介绍页；静态模式可实现模板限定的局部演示操作，但不实现复杂多步骤业务联动或真实业务动作；可交互模式再实现需求确认范围内的可复现前端交互。设计时：

- 复用项目已有组件、字体、图标和设计 token；无既有体系时建立最小一致的 token。
- 保持稳定尺寸、响应式约束和清晰的信息层级。
- 完成目标场景自然需要的控件、状态和反馈。
- 文字不得溢出、遮挡或与相邻内容冲突。
- HTML 与 `原型数据.json` 存在时，二者的页面名、文案、颜色和结构必须一致。

### 4. 预览、检查与迭代

启动本地预览后至少检查目标桌面尺寸；涉及响应式时同时检查移动端。优先用截图和可见页面状态验证：

- 页面非空，核心内容处于首屏预期位置。
- 文案、品牌、按钮、输入、卡片和状态完整。
- 没有重叠、裁切、异常滚动和布局跳动。
- 图片、图标、字体和交互均正常加载。

根据反馈修改当前可修改评审阶段的 HTML 设计源；涉及业务含义时先同步本阶段 PRD，再重新预览。新阶段或新版使用对应副本，不修改历史 HTML 或旧 Figma 节点。Figma 中的临时手工调整不得成为未经确认的新事实源。

### 5. 获得 Figma 写入确认

HTML 调整完成后，向用户说明：

- 本次定稿内容。
- 目标 Figma 文件和目标页面或节点。
- 将新增、更新或覆盖的范围。
- 预期生成的根 Frame 名称与尺寸。

确认覆盖本次目标与范围后才执行 Figma 写入；既有明确授权无需重复询问。删除节点、覆盖既有 Frame 或清理重复页面时，须列出保留项和删除项；冻结阶段的节点和链接目标不得覆盖。

### 6. 通过本地路径写入 Figma

写入前读取 [本地插件调用规范](references/本地插件调用规范.md)，选择当前环境可用的本地插件或桌面端控制方式。

默认执行原则：

1. 从 URL 解析 `fileKey` 与 `nodeId`，不要猜测目标。
2. 验证本地 Figma 文件、页面、选区和插件连接状态。
3. 读取目标页面或节点的实际结构；有参考节点时获取设计上下文和截图。
4. 空白文件可直接按已确认 HTML 创建原生节点；已有页面先识别可复用组件、变量和样式。
5. 复杂页面按根 Frame、主要分区、组件内容、修正与验证分段写入。
6. 每次写入返回全部新增或修改节点 ID；后续调用使用实际返回的字符串 ID。
7. 新增顶层 Frame 避开既有内容，除非用户已确认覆盖指定节点。

### 7. 回读验证并交付

写入后必须同时完成视觉和结构验证：

- 对根 Frame 获取截图，检查空白、重叠、裁切、字体、颜色和主要间距。
- 回读根 Frame 的尺寸、子层级、关键文本和节点数量。
- 检查所有必需文案和关键状态是否存在。
- 发现问题时先读取实际节点名称、ID、字符和尺寸，再做最小修正；修正后重新截图。

交付时返回：

- 目标 Figma 链接，优先带根 Frame 的 `node-id`。
- 根 Frame 名称、节点 ID 和尺寸。
- 关键分区或组件节点 ID。
- 已完成的视觉与结构校验结果。
- 与 HTML 定稿仍存在的差异；无差异时明确说明。

## 远程 MCP 备用路径

仅在以下情况读取 [Figma MCP 写入规范](references/Figma_MCP写入规范.md)：

- 用户明确要求使用远程 Figma MCP。
- 本地插件、桌面端或其他本地可控路径不可行，并且用户已确认切换。

切换前说明失败证据、备用路径、额外影响和需要用户执行的步骤。一次同步任务中不要混用 MCP 和本地插件写同一节点范围，以免生成重复页面或图层。

## 停止条件

- 本地 Figma 文件、页面或写入范围无法验证：停止写入并报告具体问题。
- 同一技术错误在修正参数或脚本后仍连续失败两次：停止重复写入，回读当前节点状态并提出下一步。
- 目标节点与用户确认范围不一致：停止并重新确认，不扩大覆盖范围。
- HTML 尚未定稿或用户要求继续调整：停留在 HTML 阶段，不提前写入 Figma。
